# v0.1.0 live runs — 2026-09-12

Nine user-like runs of the real engine against the live network, on this machine.
Nothing here is a fixture: every number is wall-clock or copied from the run's own
output. Task 7.2 of the phase-7 plan; the runs are the release evidence for v0.1.0.

- machine: Darwin arm64 (Apple Silicon), `CoreMLExecutionProvider` for NLI
- models: `BAAI/bge-small-en-v1.5` + `cross-encoder/nli-deberta-v3-base@6c749ce:model_qint8_arm64`
  (already downloaded; a first ever run pulls ~250 MB into the model cache)
- thresholds: `decide=0.45`, `medium=0.457948`, `high=0.99933` (`docs/eval/2026-09-12-tiers.md`)
- cache: emptied with `proofpath cache clear` before run 1, so run 1 is genuinely cold
- config: `permissions.network = allow`, `permissions.install_browser = ask`,
  `fetch.respect_robots = true`, a contact address set (Crossref/OpenAlex polite pool)
- reports were written into a scratch directory so the repository stays clean

### Cached run

and no claim is scored again. What is left is **resolution and the retraction check,
12.6 s + 1.7 s of network on every run**: they are not cached (OPEN-ITEMS 10.8), and
they are now 94 % of a warm run's wall clock.

### Two things that went wrong, recorded as they happened

**(a) A real reference was called a ghost — product rule 3, and a release gate.**
Reference [3] is `Array programming with NumPy`, Nature 585, 357-362 (2020),
`10.1038/s41586-020-2649-2` — a real paper, cited with its correct DOI. The run
reports:

```
error[ghost-reference]: cited source does not exist
   = note: DOI 10.1038/s41586-020-2649-2 resolves to a different work
```

Crossref returns the right record; the field comparison throws it away.
`resolve.title_segments` splits the raw string into title-like spans, and the
tussenvoegsel in `van der Walt, S. J.` defeats `_strip_authors`, so `segments[0]`
is `van der Walt, S` rather than the title. `title_score` returns `0.0` the moment
the candidate title shares no token with `segments[0]`, so title agreement is 0.0
with author and year both agreeing, and the reference falls through to `GHOST`.
Reproduced in three lines:

```python
>>> resolve.title_segments("Harris, C. R., Millman, K. J., van der Walt, S. J. et al. "
...                        "Array programming with NumPy. Nature 585, 357-362 (2020).")
['van der Walt, S', 'et al', 'Array programming with NumPy']
>>> resolve.title_score("Array programming with NumPy", _that_string)
0.0
```

Replacing `van der Walt, S. J.` with any ordinary surname in the same string gives
`['Array programming with NumPy']` and `title_score == 1.0`. The hand-built ghost set
scored a 0 % false-ghost rate (`docs/eval/2026-09-11-ghosts.md`) and contains no name
with a particle, so the gate never saw this class. **This is a release blocker for the
false-ghost gate, not a cosmetic miss.** Not fixed here: task 7.2 does not own
`resolve.py`, and tuning code during a release-evidence run would invalidate the run.

**(b) The fabricated reference was reported as "not in indexes", not as a ghost.**
Reference [7] is invented. It was reported honestly — it is a finding, it is
`UNVERIFIED`, the exit code is 1 — but as:

```
warning[unverified]: source is not in bibliographic indexes
   = note: web page, report or organisation-authored document; not covered by indexes
```

`resolve.looks_unindexed` decides "no person-style author list at all" with
`_strip_authors(raw) == raw`, and `Reference.raw` keeps its printed marker (a Phase 5
decision), so the string it sees begins `[7] Marchetti, L. R., …`. `_strip_authors`
anchors at the start, the leading `[7] ` blocks it, nothing is stripped, and every
unresolvable entry of a *numbered* bibliography takes the `NOT_INDEXED` exit instead
of the `GHOST` one. Strip the marker and the same string resolves to `GHOST` as the
ghost set expects. The ghost set was measured on unmarked strings, so this too was
invisible to the gate: **`check` on a numbered bibliography currently reports
approximately no ghosts at all.** Honest under rule 2, understated under §8.

Both are the same shape of defect: `resolve.py` is measured on bare reference strings
and used on marked-up ones inside a real document.

### The same document, verified twice, disagrees with itself

The two runs are 3 minutes apart on an unchanged file, and the second one calls

availability: the cold run left 7 references `UNVERIFIED (provider unavailable)`
(Semantic Scholar 429s), and on the warm run those providers answered — after which
the same field comparison that produced defect (a) below turned six of them into
ghost calls. A reference's verdict therefore depends on how busy a provider was,
which is the opposite of what §8 promises, and it is only visible because the run
was repeated.

### The false-ghost rate on a real document

All five cold-run ghosts are real, correctly cited papers with correct identifiers:

| ref | paper | note the run printed |
|---|---|---|
| [7] | Clark & Gardner, *Simple and Effective Multi-Paragraph Reading Comprehension* | `arXiv:1710.10723 resolves to a different work` |
| [10] | Dunn et al., *SearchQA* | `arXiv:1704.05179 resolves to a different work` |
| [53] | Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond* | `DOI 10.1561/1500000019 resolves to a different work` |
| [57] | Thorne & Vlachos, *Avoiding catastrophic forgetting…* | `arXiv:2004.14366 resolves to a different work` |
| [67] | Zhang & Bansal, *Addressing semantic drift…* | `DOI 10.18653/v1/D19-1253 resolves to a different work` |

That is **5 of 68 (7.4 %) on the cold run and 11 of 68 (16 %) on the warm one**,
against a hand-set gate of 0 %. The mechanism is the same as in run 1, and this run
shows how common the trigger is:

```
>>> resolve.title_segments(references[7])
['Christopher Clark and Matt Gardner',
 'Simple and Effective Multi-Paragraph Reading Compre- hension', ...]
>>> resolve.title_segments(references[53])
['Stephen Robertson and Hugo Zaragoza',
 'The probabilistic relevance framework: Bm25 and beyond', ...]
```

`_looks_like_authors` needs at least two commas to recognise a segment as an author
list, so **"First Last and First Last"** — the ordinary two-author form of every CS
bibliography — is never stripped. It becomes `segments[0]`, shares no token with the
candidate title, and `title_score` short-circuits to `0.0` with author and year
agreeing. The hand-built ghost set is written with initials (`Harris, C. R.`), which
`_strip_authors` does handle, which is why the 0 % gate never saw this.

**Read together with run 1, the false-ghost release gate is not met in the field.**
The measured 0 % is a property of the hand set's citation style, not of the resolver.
(Both runs in this section predate task 7.3's fix; see the last section of this file
for what that fix changes and what it leaves open.)

## 5. No TTY: `check … | cat`

```
$ proofpath check tests/data/draft-live.md --out run5-report.md | cat
```

Nothing prompted — product rule 4 holds, and the `browser` and `skipped` lines are
absent because no source needed the browser step (every source came from the cache
or from Semantic Scholar). Coverage on this run: `fulltext 72% / abstract 14% /
unverified 14%`, `7 refs: 1 ghost, 2 unsupported, 4 ok`, footer 28.9 s.

**The process then aborted with exit code 134.** After the whole report had been
written and printed:

```
run5-report.md written  ·  0 API calls  ·  28.9s
libc++abi: terminating due to uncaught exception of type std::__1::system_error:
  recursive_mutex lock failed: Invalid argument
EXIT=134
```

The run itself was complete and correct; the crash is in interpreter teardown, and
the only thing loaded that owns native threads is the ONNX/CoreML session. Exit codes
are part of proofpath's interface (spec §13.3: `0` / `1` / `2`, "CI can gate on this
without parsing text") and **134 is not one of them** — a CI job piping the output
would see an unknown hard failure on a run that succeeded.

### 5b. Is it reproducible? Not reliably

The same piped command was run twice more against the warm cache: both exited **1**,
with complete reports (11.8 s and 17.1 s). So the abort is intermittent — one in
three here — which is worse for a CI gate than a deterministic failure, not better,
and it is the reason this is recorded rather than dismissed. No retry loop was added
and no code was touched; the fault is filed as an observation, not diagnosed.

## 7. `scripts/zero_network_check.py` — what the cache actually carries

The script replaces `httpx.Client.send` and `curl_cffi.requests.get` with a guard
that counts the attempt and then fails it the way a pulled cable would (an
`httpx.ConnectError`, so the providers' own handling turns it into a reported
state instead of a traceback), then verifies the same draft again with a fresh
`Engine.default`.

```
$ uv run python scripts/zero_network_check.py
target       tests/data/draft-live.md
exit code    1
coverage     fulltext 0% / abstract 0% / unverified 100%
stage        Parsing      text                         0.0s
stage        Claims       rules                        0.0s
stage        Resolving    Crossref, Semantic Scholar   39.3s
stage        Retractions  Retraction Watch             0.0s
stage        Fetching     none                         0.0s
stage        Verifying    coreml                       0.0s
blocked      57 attempt(s) by module: {'polite': 57}
```

Wall clock 39.9 s, and the run finished: nothing escaped as an exception.

**What this proves — and what it does not.** All 57 blocked attempts come from
`polite.py`, the provider client; `fetch.py` and `oa.py` attempted **zero** network
calls. That is not evidence that the source text came from the cache: the ladder
never ran, because resolution produced no identifiers to fetch with, so there was
nothing for it to attempt. The evidence for cached text is section 1's cached run —
`Fetching  cache  4 full text, 1 abstract, 0 unverified  0.0s` — not this one.

**What it disproves.** The run's coverage is `fulltext 0% / unverified 100%`, not the
`57% / 14% / 29%` of the cached run in section 1. A warm cache does not make the run
offline: reference resolution is not cached (OPEN-ITEMS 10.8), so with the network
gone nothing resolves, no source identifier is produced, and the cached text is
therefore never asked for. The cache is downstream of a stage that is not cached.
An earlier version of this script used a bespoke exception and the first blocked call
aborted `prepare` outright (OPEN-ITEMS 10.6) — another reason a run cannot currently
survive losing the network mid-way.

## 8. `--allow-browser` on a source the coverage run left blocked

`10.1016/j.tibs.2014.10.005` is one of the 12 DOIs the 2026-09-11 coverage run left
at `UNVERIFIED (blocked, browser not permitted)` (an Elsevier landing page).

```
$ proofpath fetch 10.1016/j.tibs.2014.10.005 --allow-browser

install    $ uv pip install --python /…/.venv/bin/python3 scrapling[fetchers]>=0.4.15

           package and cannot be directly executed

```

Wall clock 15.4 s, exit **1**. Run once; not retried.

**The consent-gated browser step cannot install itself.** The install log reads
correctly line by line and the outcome is reported honestly — the state stays
`UNVERIFIED (blocked, browser not permitted)`, the skipped count is printed, nothing
is claimed about the source — so rules 2 and 5 hold. But the feature does not work:

1. `python -m pip install …` fails because a uv-managed virtualenv has no `pip`.
   Handled: the `uv pip` fallback is tried next and **succeeds** (`exit 0`).
2. `python -m scrapling install`, the step that actually downloads the browser,
   fails: `scrapling` ships no `__main__`, so it cannot be run with `-m`. The
   package installs a `scrapling` console script instead, which is what
   `browser.py` should call.

Verified after the run: `.venv/bin/scrapling` and `.venv/bin/playwright` both exist
and `import scrapling` succeeds, and `.venv` grew from ~345 MB to 625 MB — so the
~280 MB of Python packages did land, and only the last line of the sequence is
wrong. The browser *binaries* were **not** downloaded, and that step was deliberately
not run by hand: doing so would install several hundred MB more than the one install
the user sanctioned (rule 5). So step 3 of the ladder is still unexercised end to end
in v0.1, and the 12 blocked DOIs of the coverage run remain blocked.

genuinely offline re-run.

## 8b. After Task 7.4 — the browser step installs itself

`browser.install_commands()` ran `python -m scrapling install` as its third step.
scrapling 0.4.15 ships no `scrapling.__main__`, so that step could never succeed:

```
$ .venv/bin/python3 -m scrapling install
.../python3: No module named scrapling.__main__; 'scrapling' is a package and
cannot be directly executed
EXIT=1
```

Its CLI is the console script `scrapling` = `scrapling.cli:main`, a click group
(`install`, `shell`, `extract`, `mcp`). The step is now that same entry point reached
in-process. Click reads `sys.argv[1:]`, which under `-c` is exactly what follows the
code string, so `install` arrives as the subcommand. There is no fallback behind it:
`.venv/bin/scrapling` is this same interpreter running this same import, so it could
not rescue an import failure and would only start the ~200 MB download again. A
failed install is reported with its log instead. The real install, run once:

```
$ python -c "from proofpath import browser; log=[]; print(browser.install(log)); \
             print('\n'.join(log))"
install() -> True
$ /Users/…/.venv/bin/python3 -m pip install 'scrapling[fetchers]>=0.4.15'
exit 1
/Users/…/.venv/bin/python3: No module named pip
$ uv pip install --python /Users/…/.venv/bin/python3 'scrapling[fetchers]>=0.4.15'
exit 0
$ /Users/…/.venv/bin/python3 -c 'from scrapling.cli import main; main()' install
exit 0
```

The log is quoted with `shlex.join`, so the lines a user is shown when an install
fails are lines they can paste straight back into a shell.

Both fallbacks fired on the same run: this venv is uv-managed and has no `pip`, which
is the case the `uv pip install` step exists for. The fetch that motivated the fix
now reaches the paywalled landing page through step 3:

```
$ proofpath fetch 10.1016/j.tibs.2014.10.005 --allow-browser
evidence   fulltext
source     landing
words      3632
attempt    landing       ok                          step 3   3632 words
browser    --allow-browser
EXIT=0
```

The venv is **625 MB** with the browser engine in it, against roughly 345 MB without.
The README's install section now says so, and names
`proofpath config set permissions.install_browser never` for readers who would rather
never be asked.

**One gap left open, deliberately.** `browser.is_installed()` tests that `patchright`
and `scrapling` are *importable*, not that a chromium binary exists. The failed
installs of section 8 left this venv in exactly that state — wheels in, browser out —
and a machine in that state skips the installer and fails in `fetch_with_browser`
instead. It did not bite here because the browser binary was already in the shared
cache. Checking for the binary belongs with the consent gate and is filed, not fixed.
